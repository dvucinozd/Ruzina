# JC1060: 200 MHz PSRAM brings the longest USB audio fill under 3 ms

Date: 2026-11-04. Branch: `ogranak/jc1060-psram-200m`, stacked on
`ogranak/jc1060-flash-qio80` (`787bd1f`).

## Problem

After [QIO 80 MHz flash](2026-11-04-flash-qio80.md), the longest USB audio
fill was 3.3 ms in production and 3.8 ms with profiling. The render graph was
almost all of it. It reads both decks' PCM rings, and the decoder state and
heap live in PSRAM too. The build ran the HEX PSRAM at 80 MHz; the vendor demo
configurations use 200 MHz.

## Change

- **`sdkconfig.sd-rust-load.defaults`:** `CONFIG_SPIRAM_SPEED_200M`. It is
  IDF 6.1's default for the P4, and it is available below chip revision v3.
  250 MHz needs v3.
- **`tools/check_config.cmake`:** the guard allowed 80 MHz only. It now also
  allows 200 MHz for the load and deck profiles. The memory and touch
  diagnostics keep their qualified 80 MHz, and every other speed is still
  refused.
- **`tools/build_legacy.py`:** the load and deck variants now require
  `CONFIG_SPIRAM_SPEED=200` and `CONFIG_SPIRAM_MEMTEST=y`. The full PSRAM
  memory test runs at every boot.
- **`tools/tests/test_config.py`:** new guard cases:

  | Configuration | Guard |
  |---|---|
  | load profile at 200 MHz | accepted |
  | load profile at 250 MHz or 20 MHz | refused |
  | memory task at 200 MHz | refused |

  All 50 tool tests pass, 8 skipped.

## Device comparison (s19)

Image: `deck-engine --uac-profile` with QIO 80 MHz flash and 200 MHz PSRAM
(app `a4b0707c…`).

- **Boot:** `esp_psram: Speed: 200MHz` and `SPI SRAM memory test OK` over all
  32 MB. The chip is an AP generation-4 256 Mbit HEX PSRAM.
- **Test:** the same as s17: FLAC and MP3 together, hot cue seeks on both
  decks, about 3 min of streaming.

| | s17 (PSRAM 80 MHz) | s19 (PSRAM 200 MHz) |
|---|---:|---:|
| Fills | 18029 | 16026 |
| Longest fill | 3816 µs | **2777 µs** |
| Fills over 3 ms | 12 | **0** |
| Longest graph stage | 2683 µs | **2158 µs** |
| Longest pack stage | 857 µs | **597 µs** |
| Worst seek, FLAC / MP3 (`prime_max_us`) | 35 / 22 ms | 35 / 24 ms |
| Underruns | 0/0 | 0/0 |
| `packet_errors` | 0 | 0 |

- **Tail:** the longest fill and the slow tail improved clearly.
- **Typical fill:** it did not get shorter. Fills up to 1 ms went from 47 % to
  32 %, mostly because the graph more often took over 1 ms.
  - Each figure comes from a single run that played different parts of the
    tracks, so the medians are not directly comparable.
  - The bound that matters for dropouts is the longest fill, now under 3 ms.

## Open

- **Typical graph time:** about 1 to 2 ms per fill. One option is the graph's
  hot path in IRAM.
- **Soak:** there has been no soak longer than a few minutes with QIO flash
  and 200 MHz PSRAM.
- **Untagged VBR MP3** seeks still decode from the start.
