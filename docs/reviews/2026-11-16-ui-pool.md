# JC1060: the deck screen's small allocations come from a pool

Date: 2026-11-16. Branch: `ogranak/jc1060-ui-pool`, from `main` at `7df8005`.

## Problem

[The screen draw review](2026-11-16-screen-draw-speed.md) left Slint's scene preparation
at about half of a big frame. In each slow frame (s122) Slint allocated and freed 1000
to 3500 small objects through IDF's locked heap:
- each call took about 2.5 µs;
- that was 4.6 to 8.7 ms per frame.

## Change

`rust-core/src/idf_alloc.rs` and the new `idf_alloc/pool.rs`:
- **The screen task registers itself once** (`serve_task`, which replaces
  `count_task`). It takes a 1 MB arena from PSRAM.
- **The task's small allocations come from the arena:**
  - allocations up to 256 bytes with alignment up to 16;
  - one free list per 16-byte size class;
  - a freed block goes back to its class's list and is handed out first;
  - blocks never go back to the IDF heap.
- **No lock on the task's own path.** Only the registered task takes blocks, carves new
  ones and keeps its lists, so those steps need no lock.
- **Other tasks can still free a pool block.** One that does pushes it on its class's
  lock-free list. The screen task takes that whole list when its own list runs empty.
- **Everything else stays on IDF's PSRAM heap:** larger or more aligned allocations,
  other tasks' allocations, and the screen task's allocations once the arena is used up.
- **The slow-frame log still counts** the task's allocations and their time (event 29).
