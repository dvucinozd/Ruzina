# JC1060: QIO 80 MHz flash shortens the USB audio fill

Date: 2026-11-04. Branch: `ogranak/jc1060-flash-qio80`, stacked on
`ogranak/jc1060-sd-multisector` (`2d1e777`).

## Problem

In the [multi-sector run](2026-11-04-sd-multisector.md) the longest USB audio
fill was about 5.5 ms; the headroom target is 3 ms. Each fill renders and packs
6 ms of audio (six 1 ms packets), so 5.5 ms left almost no slack. The earlier
callback profiles (2026-11-01 to 11-02) were all taken with no deck loaded.

## Measurement with both decks playing (s16)

Image: `deck-engine --uac-profile` built from `2d1e777` (app `0c8c3e29…`). The
only change from s15 is the profile instrumentation.

- **Test:** deck 1 played FLAC and deck 2 MP3, both playing, with hot cue seeks
  on both decks; about 3 min of streaming.
- **Calibration:** the scheduler and IRQ calibrations passed.
- **Fills:** 19029 fills.

  | Fill time | Fills | Share |
  |---|---:|---:|
  | up to 1 ms | 5440 | 28.6 % |
  | 1 to 3 ms | 12526 | 65.8 % |
  | over 3 ms | 1063 | 5.6 % |
  | 6 ms or more | 0 | 0 % |

- **Worst fill (5938 µs, 3 render blocks), by stage:**

  | Stage | µs |
  |---|---:|
  | graph | 3315 |
  | pack | 674 |
  | transport | 446 |
  | progress | 391 |
  | control | 372 |
  | init | 242 |
  | other | 207 |
  | copy | 193 |

  IRQ dispatch inside the fill took 382 µs, with no task switch.
- **Main costs:**
  - The render graph dominates. It took 1 to 3 ms in 68 % of fills.
  - Packing never exceeded 0.93 ms.
- **Code placement:**
  - The graph's arithmetic is light: linear resampler, three-band EQ, SVF
    filter and limiter. All of it (about 5 KB of code) runs from flash
    through the 128 KB L2 cache, while the other core decodes MP3 and FLAC
    through the same cache.
  - A rough static count puts the work at about 0.3 ms per 128-frame block.
    The device took 0.6 to 1.1 ms.
- **Flash mode:** the bring-up `sdkconfig.defaults` set flash to DIO at
  40 MHz. The vendor demo configurations for this board use QIO.

## Change

`sdkconfig.defaults`: `CONFIG_ESPTOOLPY_FLASHMODE_QIO` and
`CONFIG_ESPTOOLPY_FLASHFREQ_80M`, replacing DIO and 40 MHz.

- **Image header:** it still says DIO. That is IDF's convention: the ROM
  starts in DIO and the second-stage bootloader switches to QIO.
- **Boot log:** the bootloader prints `SPI Mode: QIO` and
  `SPI Speed: 80MHz`.

## Device comparison (s17)

Image: the same profile build with only the flash mode and frequency changed
(app `59a59a05…`). The test was the same: FLAC and MP3 together, hot cue
seeks on both decks, about 3 min.

| | s16 (DIO 40 MHz) | s17 (QIO 80 MHz) |
|---|---:|---:|
| Fills | 19029 | 18029 |
| Longest fill | 5938 µs | **3816 µs** |
| Fills over 3 ms | 1063 (5.6 %) | **12 (0.07 %)** |
| Fills up to 1 ms | 28.6 % | **46.6 %** |
| Longest graph stage | 3315 µs | 2683 µs |
| Transport, control, progress and other (worst fill) | 1416 µs | **315 µs** |
| Worst seek, FLAC / MP3 (`prime_max_us`) | 83 / 54 ms | **35 / 22 ms** |
| Underruns | 0/0 | 0/0 |
| `packet_errors` | 1 | 0 |

- **Code fetch:**
  - Much of the fill time was spent fetching code from flash.
  - The rarely run stages gained the most, because their code is the most
    likely to have left the cache.
  - The decoders also got faster, so seeks prime in less than half the time.
- **Graph:** the render graph is now nearly all of the remaining cost. The
  longest fill is still above the 3 ms target.

## Open

- **Fill time:** the longest fill is still above the 3 ms target: 3.3 ms in
  production and 3.8 ms with profiling. The render graph is most of it.
- **Remaining candidates**, one experiment at a time:
  - PSRAM at 200 MHz, as the vendor demo uses. The PCM rings and decoder
    state live in PSRAM; the build now runs it at 80 MHz.
  - The graph's hot path in IRAM.
- **Untagged VBR MP3** seeks still decode from the start.
