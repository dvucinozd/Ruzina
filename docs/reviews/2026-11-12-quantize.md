# JC1060: quantize on the beat grid

Date: 2026-11-12. Branch: `ogranak/jc1060-quantize`, on [beat sync](2026-11-11-beat-sync.md).

## Problem

Loops, cues and Beat Loops landed wherever the deck was, by the BPM alone:
- the legacy engine passed the deck state no analysis;
- Quantize started off, as it does on the native firmware.

## Change

- **Engine:**
  - Quantize starts on, as in rekordbox.
  - The deck state gets the loaded tracks' beat grids (from the beat sync's mailbox)
    for every control except SYNC and Beat Jump.
  - With Quantize on, CUE, Loop In and Loop Out already landed on the nearest beat.
- **Deck state (`ruzina-deck`):** with Quantize on, a Beat Loop (and so 4 BEAT) also
  starts on the nearest beat, and a new Hot Cue is set there. The native firmware
  starts with Quantize off, so its behaviour only changes when Quantize is turned on.
- **Beat Jump** stays on the BPM. It moves by whole beats from wherever the deck is,
  so it keeps its place in the beat and a synced deck stays in phase. The deck state's
  grid jump lands on a beat, which would move a synced deck by up to half a beat.

## Evidence

- **Host:** 2 new tests:
  - deck state: Beat Loop start and Hot Cue on the beat;
  - engine: Loop In and Hot Cue on the beat, Beat Jump keeping its offset.

  These also pass:
  - the `ruzina-deck` tests and the host workspace;
  - the legacy feature sets;
  - target clippy.
- **Device** (`s74-quantize-*`, app `c0596749…`), owner verdict "Radi":
  - beat sync jumps with a phase error of −1 and 0 ms;
  - underruns 0/0, `packet_errors=0`;
  - longest fill 5.9 ms, over the 5 ms target. The log does not say whether a scratch
    was running at the time.
