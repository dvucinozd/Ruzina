# JC1060: keeping the screen's memory work out of the USB audio fills

Date: 2026-11-22. Branch: `ogranak/jc1060-fill-gap`, after
[what slows the USB audio fill in play](2026-11-21-fill-contention.md).

## Question

The s163 profile showed what slows Master Tempo fills:

- 88 % of the Master Tempo fills over 3 ms ran while the screen drew a frame.
- With the screen still, only 1.7 % went over 3 ms, against 18.3 % while it drew.
- The longest fill was 5350 µs.

The goal is Master Tempo under 5 ms ([the accepted scratch fill](2026-11-20-scratch-mt-fills.md)).

## The boot bench: CPU writes to PSRAM, not the PPA

s165 timed one fill with each kind of screen work running on the other core at the same
time. This bench is behind `--contention-bench` and never goes into a play image.

| Work on the other core | Plain fill | Master Tempo fill |
| --- | --- | --- |
| PPA move | +19 µs | |
| Flush | +16 µs | |
| CPU drawing | +820 µs | +1400 µs |
| CPU copying | +1900 µs | +3740 µs |

The fills slow down when the CPU writes to the frame buffers in PSRAM. The PPA moving
memory barely matters.

s165 left artefacts at the screen edges. s162 and s164 had none, so the bench caused them.
The cause was not found, and that is why the bench now has its own flag.

## Now

- **The gate (`main/fill_gap.h`, `Gate` in `slint_ui.rs`):** the screen splits a frame into
  three steps:
  - Slint's lines;
  - the PPA moving a lane;
  - a lane's new columns.

  Before each step, the screen waits, asleep, for a gap between USB audio fills long enough
  for that step, judged by the step's recent mean time.
- **Lanes:** the lanes' columns, playhead and flags are drawn into a 64-column strip in
  internal RAM. The PPA then copies them into the frame buffer (`ruzina_panel_strip`,
  `ruzina_panel_blit`). Without a strip, or if a copy fails, the CPU draws them and flushes.
- **Slint's lines** go through the same strip, now 16×1024 px (32 KiB) and shared with the
  lanes. Through the PPA they reach the frame buffer in blocks (`ruzina_screen_lines::Stage`,
  `copy_block`).
- **`lines_us` (dd0bd8b):** it counted the copy of a band twice when the next line finished
  the band. It now counts only the line, and a host test covers it. This changes only how
  the slow-frame log splits a frame, not the drawing.
- **Profile images:**
  - Activity bits and step times for the move and the flush (events 33–36, means 43–46).
  - `--fill-gap-cycle` turns the gate off every other 30 s, so one run measures both.
    Phase 0 is the gate on and phase 1 is the gate off.

## On the board

Each image ran for 15 minutes with the FLX4, as in the s163 run: the soak DJ alone first,
then Master Tempo on both decks. Every run had 0/0 underruns and no panics.

- s163 had no strip, no gate and no PPA copies.
- s169 and s170 are builds from before the rebase onto `7a5ea74`, with the same fill path
  as this branch and the same base as s163.
- The `lines_us` fix came later and changes only the log, so the measured images were not
  rebuilt.

Master Tempo fills:

| Image | Screen | Over 3 ms | Longest | Mean |
| --- | --- | --- | --- | --- |
| s163 | drawing | 18.3 % | 5350 µs | 2596 µs |
| s163 | still | 1.7 % | 3914 µs | 2275 µs |
| s169, lanes via PPA | gate off | 15.2 % | 4438 µs | 2546 µs |
| s169, lanes via PPA | gate on | 6.0 % | 4110 µs | 2377 µs |
| s170, lanes and Slint via PPA | gate off | 14.0 % | 4263 µs | 2520 µs |
| s170, lanes and Slint via PPA | gate on | 5.5 % | 4168 µs | 2367 µs |

- s170 is app `1022536c…`; s169 is app `5370cffd…`.
- Plain fills stayed under 3 ms in nearly all cases: at most 0.2 %. Their longest was
  4603 µs, on s169 with the gate off.
- **Reading:**
  - Moving the CPU's writes to the PPA alone helps a little: 18.3 % falls to 14–15 %, and
    the longest fill drops by about 1 ms.
  - The gate does most of the work: 5.5–6 % over 3 ms.
  - With both, every Master Tempo fill stayed under 5 ms.
- **Screen cost on s170:** a deck-page Slint step took the same as on s169 (2.2 ms). A
  full-screen frame is about 5 ms slower, because of about 80 PPA block copies (about
  12 ms). The owner checked every page on s169 and s170, and the lanes and pages look right.
- **Evidence:** the tables are `s163-overlap.txt`, `s169-flx4-overlap.txt` and
  `s170-flx4-overlap.txt` in `D:\BoardEvidence\JC1060-20261030-COM3`.
  - The s169 build lost its Rust archive in an evidence cleanup.
  - Its flash images and app hash are intact, so the flash checked those and skipped only
    the archive (`skipped_artifacts`).
  - A rebuild from the same sources is kept beside it, with a note.
