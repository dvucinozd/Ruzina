## Verified factory layout

Source: independent full backup `factory-esptool56-read-1.bin` in
`D:/BoardEvidence/JC1060-20261030-COM3`. Whole-file SHA-256 verified:
`27d5782978aeb3c42f8b49659e793d3ca8f59543f62e419d7b1981de2c492060`.
The matching second read and secondary copies are retained. Never put dumps,
NVS values or complete factory logs into Git.

Scanning sector boundaries below 0x10000 found the partition table at 0x8000.
Its ordered 32-byte records have the expected 0x50AA magic; the terminating
0xEBEB MD5 record matches the records. All partition bounds fit the observed
flash and do not overlap. esptool 5.6 parsed P4 image headers at 0x2000 and
0x10000; both declare chip ID 18 and revision range 100..199. Boot entry points
are respectively 0x4ff29eda and 0x4ff003f8. Header parsing is not a signature,
full image integrity or restore execution test.

## Proposed first flash-backed diagnostic layout review

The current build-only scalar app uses the IDF default single-app table,
bootloader offset 0x2000, partition offset 0x8000, app offset 0x10000.
Coinciding offsets do not make its partition definitions equivalent to factory.
Before writing, bind an exact NEW manifest, `flasher_args.json`, bootloader,
partition binary and app binary. List byte lengths plus erase-sector-rounded
ranges; check pairwise overlap and flash bounds. The current package manifest
must include those bootloader/partition inputs before it can be a write plan.

| Potential write | Changed contents / consequence | Recovery source |
|---|---|---|
| Bootloader at 0x2000 | Replaces factory startup with pinned IDF 6.1 startup | Exact bytes from verified whole-flash backup |
| Table at 0x8000 | Replaces factory partition authority; factory storage may become unreachable | Original 0x8000 sector from backup |
| Diagnostic app at 0x10000 | Overwrites beginning of factory executable, preventing its normal use | Original app region from backup |
| Any full-chip erase | Destroys NVS, storage, all executable and opaque regions | Entire 16 MiB backup at origin 0 |

The intended minimal experiment does not require full-chip erase or writes
to NVS/storage. A generic IDF layout is not approved by this document.
Do not run autogenerated write instructions, combine the factory bootloader
with an assumed-compatible app, or derive programming offsets from ELF load
addresses. Flash app startup may itself write settings: review selected
components and NVS use before relying on untouched regions staying unchanged.

The final offline flash-build-only package produced these potential write
spans, derived from its actual `flasher_args.json` and file lengths. This is
an impact inventory, not an approved write command:

| Artifact | Offset | File bytes | Erase-sector span, end exclusive |
|---|---|---|---|
| bootloader.bin | 0x2000 | 23296 | [0x2000, 0x8000) |
| partition-table.bin | 0x8000 | 3072 | [0x8000, 0x9000) |
| ruzina_legacy_probe.bin | 0x10000 | 148432 | [0x10000, 0x35000) |

These spans do not overlap NVS/PHY/storage, but replacing the partition table
changes the address-space authority. Verify the exact package hashes from the
[offline build index](readiness/jc1060-s03-offline-builds-20261030.json) and
inspect its partition definitions before finalizing a programming plan.

## Recovery procedure to complete with the operator

1. Record actual power supply, connector markings and PCB/panel photographs;
   identify all possible power sources. Disconnect external USB peripherals.
2. Establish the actual button-held/manual ROM entry sequence from that board,
   then retain a read-only chip/MAC/revision/flash-ID handshake after factory
   boot and after complete power removal. Software USB ROM entry is already
   observed; manual entry is not. Do not invent BOOT/RESET timing or pin labels.
3. Recheck both independent full backup lengths/hashes and secondary location.
   Retain an immutable copy; never use the same path for readback after writes.
4. Prepare exact files, sector ranges and recovery commands using esptool 5.6.0,
   the observed connector and 16 MiB geometry. Restore source is the complete
   verified dump at flash origin 0; preserving its bytes requires avoiding
   header rewriting. Review esptool options before final command approval.
   Specific command templates and per-sector recovery payload hashes are in
   the [S4 plan](readiness/jc1060-s04-write-recovery-plan-20261030.json); their
   Python/port/readback placeholders require a fresh verified live session.
5. After an authorized write/restore, capture readback from all affected
   sectors and compare expected bytes. A whole-chip restoration additionally
   requires full readback SHA equality to the original dump, followed by
   factory boot and operator demo observation. A hash alone is not boot proof.
6. Capture power-on, app restart, USB service reset and reconnect separately.
   Three consecutive successful repetitions per applicable scenario are the
   initial proposed smoke criterion. State whether USB removal also removes
   power. Raw cold transition capture needs a suitable independently powered
   logging path or bounded reconnect capture with the missing prefix disclosed.

## Reset analysis and stopping conditions

The historical RAM image ran scalar Rust calls, then native USB reset led to
ROM SPI_FAST_FLASH_BOOT and repeated HP_SYS_HP_WDT_RESET. ROM attach_flash
also failed. After owner-confirmed complete power removal, ROM RDID and factory
warm boot worked, and the owner confirmed the demo visible. The actual cold
transition was not captured. No flash or eFuse writes were performed.

Pinned IDF 6.1 `components/esp_system/port/soc/esp32p4/clk.c` disables the MSPI
flash clock under PURE_RAM. This is one candidate explanation, not established
causality. Native USB reset is not equivalent to complete power removal;
do not infer that either resets every peripheral domain. An ordinary flash-backed
IDF boot must be independently tested before attributing the defect solely to
RAM mode. Do not disable watchdogs or patch arbitrary registers to hide it.

Any repeated watchdog boot loop, unexpected identity, changed backup hash,
unknown flash geometry or failed ROM attach stops automated retries. Preserve
logs; use operator power removal and the documented manual recovery path.
Do not execute RAM probes without an operator available for this recovery.
The new loader's hold policy intentionally returns an incomplete-scenario exit
until operator recovery has separate evidence. No peripheral qualification
follows from this preparation.
