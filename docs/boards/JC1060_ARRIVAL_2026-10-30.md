## Observed identity and immediate boundary

The owner reports model JC1060P470C_I_W_Y connected on COM3. Windows enumerates
`USB\VID_303A&PID_1001&MI_00`, and esptool reports native USB Serial/JTAG.
The device repeatedly reports **ESP32-P4 v1.3**, not the previously expected
v3.2. esptool 5.3.1 reads eFuse word `0xa4054313` at `0x5012d04c`:
`major = (((word >> 23) & 1) << 2) | ((word >> 4) & 3) = 1`,
`minor = word & 15 = 3`, combined revision **103**.
The independently invoked installed esptool 4.12.dev1 reports the same revision
and MAC `e8:f6:0a:e7:22:1d`.

Observed flash RDID is `0x184068` in register order (manufacturer `0x68`,
device `0x4018`), decoded size **16,777,216 bytes**. Secure Boot and flash
encryption report disabled. A later factory warm boot reports **32 MiB PSRAM
at 200 MHz**, with its memory test OK; this is factory evidence, not our PSRAM
qualification. Fitted panel, PCB/module markings, actual supply path and
connector photographs remain unobserved. esptool's
generic `400MHz` features label is not a measured clock or permission to run
this legacy unit at 400 MHz.

The pinned native `esp-hal 1.2.2` explicitly excludes P4 below v3.0, and this
product's `.cargo/config.toml` and both Guition profiles require revision 302.
Therefore **native Rust C02 is BLOCKED_INCOMPATIBLE_SILICON for this unit**.
Do not lower that minimum, patch the image header or flash the prepared v3.x
kits. Espressif documents incompatible hardware/software between v1.3 and v3.x;
this is not only a version-number check.

During the initial arrival/RAM batch, read-only identification and RAM-loaded
programmer stubs were used. No
flash erase, flash write, eFuse programming or production image activation has
been performed. A passive 12-second factory console observation returned zero
bytes. A subsequent normal reset captured factory `esp_brookesia_demo 1.0.1`
on `v5.5.4-dirty`, revision v1.3, and a GT911 identity/config response.
The owner initially reported the screen unlit. After the later complete power
disconnect and verified return to factory boot, the owner confirmed the screen
displays the factory demo. This is factory behavior, not our display acceptance.

### Preferred initial boundary

Use a small C/ESP-IDF platform shell with HAL-independent Rust logic linked as
a static archive through a narrow C ABI. ESP-IDF owns startup, its legacy
linker/ROM map, FreeRTOS, interrupts, drivers, allocator and hardware recovery.
Rust retains product state machines, parsers and DSP. Do not combine native
esp-hal/esp-rtos startup with IDF startup in one executable.

The [compile experiment](../../firmware-idf/legacy-jc1060/README.md) evaluates linking the
actual `ruzina-deck` pitch conversion through a scalar ABI. It uses stable
Rust 1.95.0 and the existing bare-metal target for the archive, no `std`, no new
third-party Rust dependencies, no allocator and no HAL. Its ESP-IDF app selects
legacy silicon, 360 MHz, USB Serial/JTAG and no PSRAM or product peripherals.
Compile/link success cannot establish on-device execution, FPU context save,
audio timing, allocator correctness or the viability of every shared crate.

The initial 5.5.4 link attempt revealed a soft/single-float ABI mismatch in a
C helper object bundled with Rust's precompiled compiler-builtins. The Rust
objects themselves match IDF's single-float ABI. The 6.1 experiment explicitly
orders IDF's matching GCC runtime before the Rust archive, retaining strict
linker checks. No mismatch suppression or patched standard-library objects are
used. Full DSP/runtime compatibility remains a later measured gate.

### Executed proof and recovery limitation

The flash-backed 6.1 app built and linked. Its image header declares P4
minimum v1.0 / maximum v1.99; strict ABI checks were retained. The map selects
IDF's single-float GCC helpers. It was **not flashed**.

A separate `PURE_RAM` image (113,312 bytes, SHA-256
`fc12b85de992b0f71ba7a6b552bc68df6562498e9256cc38a30a7828f8fcc9bb`)
was loaded through ROM into reviewed legacy SRAM/SPM segments, entry point
`0x4ff00d92`. The load selects no flash offsets and writes no flash.
The on-device log reports IDF 6.1, revision 103 and CPU 360,000,000 Hz.
Two runs called shared Rust from C and returned
`0 -> 1000`, `8192 -> 0`, `16383 -> -999`, `65535 -> -999` centipercent.
The log explicitly retains `readiness=NOT_QUALIFIED`.
The hash-verified local evidence ZIP and source/artifact index are recorded in
the [RAM package index](readiness/jc1060-idf61-ram-package-20261030.json).
It includes the uncommitted experimental source snapshot, ELF/BIN/map, build
and runtime logs. It is not a release and contains no factory dump.

**Recovery remains open:** after RAM execution, native USB soft reset returned
to ROM with `SPI_FAST_FLASH_BOOT`, then repeated `HP_SYS_HP_WDT_RESET`.
ROM flash-attach also failed. A complete physical power disconnect has been
completed by the owner; subsequent ROM RDID and normal factory boot were
captured successfully. The owner also confirmed the factory display now works.
The raw cold power-on transition itself was not captured; the subsequent reset
log is not renamed as a cold-boot log. This limitation must be resolved or
bounded before regular bring-up. It is
not a successful cold boot, product reset/reconnect PASS or factory restoration.
IDF's pure-RAM clock initialization explicitly disables the MSPI flash clock;
this is a source-based explanation candidate, not a verified root cause.

An alternative is Rust `std` on `riscv32imafc-esp-espidf`. Rust documents P4
support but classifies the target as Tier 3 and requires `build-std` and
`ldproxy`. The esp-rs `esp-idf-sys` upstream is archived as of this assessment;
maintenance/provenance must be evaluated before selecting a binding/fork.
This route changes the toolchain/runtime surface more than the small archive
experiment. It is not implemented here.

### Ordered implementation gates

1. **L0 — preserve/recover.** Full backups and secondary verification are
   complete. Cold recovery was demonstrated with operator power disconnect
   followed by ROM/factory boot. Finish photographed physical identity,
   manual ROM entry and board-specific restoration /
   programming-layout review. No replacement firmware before these gates.
2. **L1 — compile/link proof (done for the narrow probe).** Retain
   revision headers, actual ELF symbol references and source/tool/artifact
   hashes. Retain generated layout as build output, not approved flash offsets.
3. **L2 — minimal physical boot.** Scalar RAM calls are observed; reset
   recovery remains open. Only after L0, program the reviewed exact
   files, retain flash readback and observe scalar Rust calls, reset causes,
   warm reset, true power cycle and service reconnect separately.
4. **L3 — memory/task proof.** IDF PSRAM identification and bounded scratch,
   allocator capabilities/ownership, two-task FPU context switching, internal
   vs external buffers and measured budgets. No product DMA claims from CPU
   scratch. No automatic 400 MHz override.
5. **L4 — display/touch then SD.** Identify actual panel; pin/hash review of
   exact BSP, licences and tables; resolve touch wiring; measure lifecycle,
   rotation and input. Then qualify read-only SD before persistence.
6. **L5 — product adapters.** Establish USB PHY/power/backfeed before host
   peripherals. Add MIDI/LED and MSC ownership, one-deck then two-deck audio,
   controller-only headphones and external MAIN fallback. C6/settings/OTA and
   stress/soak follow with their original C06/C07 acceptance requirements.

This keeps the native target recoverable and avoids duplicating Rust product
logic. The cost is a separate platform/scheduler/driver integration, independent
build CI and hardware qualification. It is not a quick sdkconfig substitution.
